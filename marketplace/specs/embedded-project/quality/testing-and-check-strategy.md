# 测试和检查策略

## 可测试设计

- MUST: CRC、ring buffer、协议解析、状态机、参数校验等模块必须优先支持单元测试。
- MUST: 硬件相关模块应通过 mock、fake 或 adapter 隔离硬件依赖。
- SHOULD: 纯逻辑模块应脱离硬件运行。

## 最小验证

- MUST: 每个项目必须在开发文档中声明可执行的 `build_command`；适用时还必须声明 `test_command` 和 `static_check_command`。
- MUST: 每次新增模块至少执行 `build_command`，或记录命令不可用的原因和替代验证方式。
- MUST: 每次修改协议、状态机、公共工具、错误码时必须说明验证方式。
- MUST: 修改 public API 时必须检查调用方。
- SHOULD: 每个模块提供最小 usage 示例或测试入口。

## 验证结果记录

- MUST: 验证结果必须记录所执行的命令、目标硬件或构建配置、结果，以及未执行检查的原因。
- MUST NOT: 不允许用“已编译”代替实际执行的命令或可追溯的替代验证。

## Agent 自检

- MUST: agent 修改代码后必须输出自检结果。
- MUST: 自检结果必须说明修改了哪些文件、属于哪一层、是否符合依赖方向、是否存在未验证内容。
- MUST NOT: agent 不得声称测试通过，除非实际执行了测试或构建命令。

## 检查顺序

1. 检查目录和层级是否正确。
2. 检查 public API 是否清晰。
3. 检查依赖方向是否单向。
4. 检查错误处理和超时路径。
5. 检查并发、ISR、DMA 影响。
6. 执行可用的构建、测试或静态检查。
